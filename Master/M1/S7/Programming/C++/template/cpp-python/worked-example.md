# A worked example: `shortest-path`, imported from Python

The C++ template's [worked example](../cpp/worked-example.md) started from this
template instead. Everything on that page holds; this one covers only what the
Python side adds. Built and run on this machine on 2026-09-14.

## The project

```
shortest-path/
├── CMakeLists.txt              this template's: one more option, BUILD_PYTHON_LIB
├── CMakePresets.json           this template's: the C++ presets plus python
├── cmake/
│   ├── pybind11.cmake          added
│   └── (the four C++ files)
├── bindings/
│   └── graphs.cpp              added
├── include/, src/, apps/, tests/, square.txt      as in the C++ example
└── build/python/               generated by the python preset
```

## Each added file and its role

| Folder | File | Role |
|---|---|---|
| root | `CMakeLists.txt` | The C++ one plus the option `BUILD_PYTHON_LIB` and the line that includes `cmake/pybind11.cmake` when it is on. Untouched from the template. |
| root | `CMakePresets.json` | The C++ presets plus `python`: `release` with `BUILD_PYTHON_LIB=ON`. Untouched. |
| `cmake/` | `pybind11.cmake` | Finds the activated env's Python and its pybind11 (or fetches pybind11), then turns each `bindings/` file into a module. Untouched. |
| `bindings/` | `graphs.cpp` | The module `graphs`, named after the file. `py::class_<Graph>` exposes the constructor, `add_edge`, `neighbours` and `vertex_count`; `m.def` exposes `shortest_path`. Glue only: no logic, no state. |

The one thing to write in `graphs.cpp` is the pairing of names:

```cpp
PYBIND11_MODULE(graphs, m) {
    py::class_<Graph>(m, "Graph")
        .def(py::init<std::size_t>(), py::arg("vertex_count"))
        .def("add_edge", &Graph::add_edge, py::arg("u"), py::arg("v"))
        .def("neighbours", &Graph::neighbours, py::arg("u"))
        .def_property_readonly("vertex_count", &Graph::vertex_count);
    m.def("shortest_path", &shortest_path, py::arg("graph"), py::arg("source"), py::arg("target"));
}
```

## How it fits with the rest

```
src/*.cpp ─► project_library ─┬─► shortest-path, benchmark, tests   (as before)
                              └─► bindings/graphs.cpp ─► build/python/graphs.cpython-311-x86_64-linux-gnu.so
                                     ▲
                                     └── pybind11 headers, from the activated conda env
```

The module links the same library the programs do, so `src/` is compiled once
and knows nothing about Python: `graphs.cpp` names entry points, pybind11
converts the arguments (`#include <pybind11/stl.h>` makes a `std::vector` a
Python list) and translates exceptions (`std::out_of_range` becomes
`IndexError`). Which Python can import the `.so` is decided at configure time
by which env is active, which is why the env is activated first.

## The commands, and what they printed

| Command | Output |
|---|---|
| `conda activate m1ai-programming` | the env whose pybind11 3.1.0 is used and whose Python will import the module |
| `cmake --preset python && cmake --build --preset python` | `Built target graphs`, plus the three C++ programs, all with `-O3` |
| `cd build/python && python`, then `import graphs` | |
| `g = graphs.Graph(5)`, four `g.add_edge(u, v)`, `graphs.shortest_path(g, 1, 3)` | `[1, 0, 3]`, the same path the C++ program printed |
| `g.neighbours(0)`, `g.vertex_count` | `[1, 3]`, `5` |
| `g.add_edge(0, 9)` | `IndexError: add_edge: vertex out of range` |

The module imports from a directory that contains the `.so`, or with that
directory on `PYTHONPATH`; installing it as a package is outside the template.
